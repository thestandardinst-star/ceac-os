## Why this programme exists

Experience V2 is technically strong and accepted, but direct comparison with the product owner's premium CEAC mockup and saved quality references showed material visual-fidelity drift. The remaining problem is not primarily functionality. It is composition, hierarchy, density, surface treatment, visual intelligence, role character and interaction quality.

A technically green screen is not automatically a visually accepted screen.

## Source-of-truth precedence

For visible product-experience work:

1. live canonical code + accepted security/domain contracts;
2. this Visual Fidelity programme;
3. repository-owned CEAC visual targets;
4. CEAC original premium mockup;
5. distilled quality parameters in `REFERENCE_MANIFEST.md`;
6. role/panel specifications;
7. existing implementation only as evidence, never as the quality ceiling.

Security, privacy, RLS, authority, finance meaning, protected HR, data integrity and truthful-data rules always outrank visual convenience.

## One-writer rule

Exactly one writer may mutate the active VF branch at a time.

Before every material write:
- refresh branch HEAD;
- compare with BUILD_STATE;
- preserve all newer canonical work;
- never reset, force-push or overwrite a newer writer;
- reconcile forward.

## Continuous execution rule

Routine commits, test runs, successful gates, screenshots, accepted substages and stage transitions are continuation points, not stopping points.

Stop only for a genuine owner decision, security/authority ambiguity, missing required credential/reference, conflicting live writer, irreversible destructive action, or an external blocker that prevents all safe forward work.

## Non-negotiable completion rule

The programme is not complete because tests pass.

Completion requires both:
- TECHNICALLY ACCEPTED; and
- VISUALLY / PRODUCT-EXPERIENCE ACCEPTED.

A screen that is functional but still feels like a generic enterprise dashboard fails visual acceptance.
